Name of Atom:
Data Upload and Validate
 
Small Description:
The Data Upload and Validate Atom enables users to upload a master data file and automatically validate future file uploads against it. It includes pre-built templates for common analytics use cases and intelligently classifies data columns for streamlined analysis workflows.
 
Keywords:
data upload, file validation, master file, template validation, column classification, identifiers, measures, dimensions mapping, promo analysis, marketing mix modeling, category forecasting, data preprocessing, MinIO storage, MongoDB logging, data governance
 
Working Process:
User Perspective:
When a user interacts with this Atom, they can either:
 
Option 1: Upload a Custom Master File
 
Upload Your Master File: You provide a primary dataset (like sales_master.csv) that serves as the validation template
 
AI Analyzes Your Data: The system automatically examines your file structure, column types, and data patterns
 
Define Your Business Dimensions: You specify key business dimensions like Product, Time Period, Market/Region, and the system maps your column identifiers to these dimensions
 
Set Validation Rules: The Atom creates validation rules based on your master file's structure
 
Option 2: Choose a Pre-Built Template
You can select from three ready-made templates:
 
Promo Analysis Template: For promotional campaign effectiveness studies
 
Marketing Mix Modeling Template: For attribution and media spend optimization
 
Category Forecasting Template: For demand planning and inventory management
 
Behind the Scenes Process:
File Processing: The system reads and analyzes the uploaded master file
 
Intelligent Column Classification:
 
Automatically separates columns into Identifiers (categorical data like product names, regions, dates)
 
And Measures (numerical data like sales, revenue, quantities)
 
Dimension Mapping: Assigns identifier columns to business dimensions you specify (e.g., Product_ID → Product dimension, Store_Location → Market dimension)
 
Validation Schema Creation: Builds a validation framework for future file uploads
 
Storage and Logging:
 
Validation files are securely stored in MinIO cloud storage
 
Column classifications, dimension mappings, and process logs are saved in MongoDB for tracking and reuse
 
Future File Validation:
When you upload subsequent files, the Atom automatically:
 
Checks if new files match the master file structure
 
Validates data types and formats
 
Flags missing columns or data inconsistencies
 
Ensures dimension mappings remain consistent
 
Output / What We Get:
This Atom generates several key outputs:
 
Validated Master File Structure: A confirmed data schema that serves as your project's foundation
 
Column Classification Report: Clear categorization of all columns as either identifiers or measures
 
Dimension Mapping Configuration: Assignment of identifier columns to business dimensions (Product, Time, Market, etc.)
 
Validation Rules: Automated checking criteria for future file uploads
 
Storage Confirmation: Secure file storage in MinIO with MongoDB logging for audit trails
 
Template Setup (if using pre-built options): Ready-to-use configurations for specific analytics use cases
 
This output enables:
 
Consistent Data Processing: All future files follow the same validated structure
 
Streamlined Analysis: Pre-classified columns make filtering and selection in other Atoms much faster
 
Error Prevention: Automatic validation catches data issues before they impact analysis
 
Audit Trail: Complete logging for data governance and compliance

The Data Upload and Validate Atom serves as the foundational gateway for your entire analytics workflow. Think of it as setting up the "rules of the game" for all your data analysis activities.

Data Consistency: In business analytics, inconsistent data structure is one of the biggest productivity killers. This Atom ensures every file you work with follows the same validated format, eliminating hours of data cleaning later.
 
Intelligent Automation: Instead of manually defining what each column represents every time you upload data, the system learns from your master file and automatically applies those learnings to future uploads.

POST: /create_new - Create Validator Atom ID with Column Preprocessing
====================================================================

Purpose
-------
Creates a new validation atom ID by uploading data files (CSV/XLSX) and automatically 
generating validation rules based on the file structure and data types.

Input Parameters
----------------
Form Data:

1. validator_atom_id (required, string)
   - Unique identifier for the validator atom.
   - Cannot be empty or contain only whitespace.

2. files (required, List[UploadFile])
   - Data files to process (CSV or XLSX format).
   - Maximum 3 files supported.
   - Supported formats: .csv, .xlsx.

3. file_keys (required, string)
   - JSON string containing keys/identifiers for each uploaded file.
   - Must match the number of uploaded files.

Process Flow
------------
1. Input Validation
   - Validates that `validator_atom_id` is not empty.
   - Ensures number of files matches number of keys.
   - Restricts the maximum number of files to 3.
   - Validates JSON format of `file_keys`.

2. Column Preprocessing
   - Strip leading/trailing whitespace from column names.
   - Convert all column names to lowercase.
   - Remove internal spaces while preserving underscores.
     Example:
       "User Name " → "username"
       "user_id "   → "user_id"

3. File Processing
   - Reads each uploaded file into a pandas DataFrame.
   - Applies column name preprocessing.
   - Extracts data types for each column:
     * numeric (int/float)
     * date (datetime)
     * boolean (bool)
     * string (default)

4. Schema Generation
   - For each file, creates a schema containing:
     * Column definitions with names and types
     * Sample data (first 3 rows)
     * Metadata (total rows and columns)
     * Column type mapping

5. Configuration Storage
   - Local file: Saves as JSON in `CUSTOM_CONFIG_DIR/{validator_atom_id}.json`
   - MongoDB: Stores validation configuration document
   - Memory cache: Stores for quick access via GET endpoints

Output Response
---------------
Success Response (HTTP 202)
---------------------------
{
  "status": "success",
  "message": "Validator atom created successfully",
  "validator_atom_id": "your_validator_id",
  "config_saved": true
}

Error Responses
---------------
HTTP 400 - Bad Request
  - Empty `validator_atom_id`
  - Invalid JSON in `file_keys`
  - File count mismatch with keys
  - Unsupported file format
  - File parsing errors

HTTP 500 - Internal Server Error
  - Configuration save failures
  - Database connection issues

Generated Assets
----------------
- JSON Configuration File: `{validator_atom_id}.json`
- MongoDB Document: Validation configuration
- Memory Cache Entry: For runtime access
- Schema Definitions: Column types and validation rules

Supported File Formats
----------------------
- CSV: Comma-separated values
- XLSX: Excel spreadsheet format

Validation Mode
---------------
Default: `"simple"` validation mode
  - Automatically infers column types from data
  - Generates basic validation rules based on data structure



GET: /view_new/{validator_atom_id} - Retrieve Validator Atom Schemas
=====================================================================

Purpose
-------
Retrieves the schema definitions for all file keys associated with a specific validator atom.
Returns only the schema data without metadata or configuration details.

Input Parameters
----------------
Path Parameters:

1. validator_atom_id (required, string)
   - Unique identifier of the validator atom to retrieve.
   - Must match an existing validator atom ID created via `/create_new`.

Process Flow
------------
1. Validation
   - Checks if `validator_atom_id` exists in the memory cache (`extraction_results`).
   - If not found, returns HTTP 404 error.

2. Data Retrieval
   - Fetches stored schema data from memory cache.
   - Extracts only the `schemas` portion of the stored data.
   - Filters out non-schema metadata such as:
     * `config_saved`
     * `config_path`
     * `validator_atom_id`

3. Response Formation
   - Returns clean schema data for all associated file keys.
   - No additional transformation or processing is applied.



POST: /classify_columns - Classify Columns into Identifiers, Measures
======================================================================================

Purpose
-------
Automatically classifies data columns into three categories:
  - Identifiers
  - Measures
  - Unclassified

Uses keyword matching and data types for auto-classification, with optional user override.
Supports both custom validator atoms and template-based validator atoms.

Input Parameters
----------------
Form Data:

1. validator_atom_id (required, string)
   - Unique identifier of the validator atom.
   - Must exist in MongoDB or memory cache.

2. file_key (required, string)
   - Specific file key within the validator atom to classify.
   - Must match an existing file key in the validator's schema.

3. identifiers (optional, string, default: "[]")
   - JSON array of column names to override as identifiers.
   - User-specified values take precedence over auto-classification.

4. measures (optional, string, default: "[]")
   - JSON array of column names to override as measures.
   - User-specified values take precedence over auto-classification.

5. unclassified (optional, string, default: "[]")
   - JSON array of column names to override as unclassified.
   - User-specified values take precedence over auto-classification.

Process Flow
------------
1. Validator Validation
   - Checks MongoDB for validator atom data.
   - Falls back to memory cache if MongoDB is unavailable.
   - Ensures `file_key` exists in schema.
   - Extracts all columns and data types.

2. User Override Processing
   - Parses user-provided JSON strings into arrays.
   - Validates columns exist in schema.
   - Detects and prevents conflicts (columns in multiple categories).
   - User overrides are prioritized over automatic classification.

3. Auto-Classification Logic
   - Keyword-based classification:

     Identifier Keywords:
       id, name, brand, market, category, region, channel, date, time, year, 
       week, month, variant, ppg, type, code, packsize, packtype

     Measure Keywords:
       sales, revenue, volume, amount, value, price, cost, profit, units, 
       d1, d2, d3, d4, d5, d6, salesvalue, baseprice, promoprice

   - Classification Rules:
     * Identifiers: match identifier keywords.
     * Measures: match measure keywords or are numeric.
     * Unclassified: all remaining columns.

4. Confidence Score Calculation
   - User-specified columns: 1.0 (100%)
   - Keyword match: 0.9 (90%)
   - Numeric type: 0.7 (70%)
   - Default fallback: 0.5 (50%)

5. Data Persistence
   - MongoDB: stores classification record with metadata.
   - Memory Cache: runtime storage for faster access.
   - Timestamp: stored in ISO 8601 format.

Output Response
---------------
Success Response (HTTP 200)
---------------------------
{
  "status": "success",
  "classified_columns": {
    "identifiers": [
      {"column": "region", "confidence": 1.0},
      ...
    ],
    "measures": [
      {"column": "sales", "confidence": 0.9},
      ...
    ],
    "unclassified": [
      {"column": "remarks", "confidence": 0.5},
      ...
    ]
  },
  "validator_atom_id": "your_validator_id",
  "file_key": "your_file_key"
}

Error Responses
---------------
HTTP 400 - Bad Request
  - Invalid or missing `file_key`
  - Invalid JSON in override parameters
  - Column listed in multiple categories
  - Unknown column name in override list
  - Internal classification conflicts

HTTP 500 - Internal Server Error
  - MongoDB save failure
  - Database connection issues

Classification Categories
-------------------------
1. Identifiers (Dimensions)
   - Purpose: Used for grouping/filtering (e.g., region, category)
   - Characteristics: Non-numeric, descriptive

2. Measures
   - Purpose: Used in aggregations/calculations (e.g., sales, volume)
   - Characteristics: Numeric, measurable

3. Unclassified
   - Purpose: Columns that do not clearly fit other categories
   - Characteristics: Descriptive, textual, or mixed data types

Key Features
------------
- Dual Validator Support:
  * Supports both custom (/create_new) and template (/validate_*) validators.

- User Override Priority:
  * User input always takes precedence.
  * Auto-classification applies only to unspecified columns.

- Confidence Scoring:
  * Helps assess certainty of each classification.
  * Guides manual review if needed.

- Data Persistence:
  * MongoDB for durability.
  * Memory cache for performance.
  * Graceful degradation if memory fails.


POST: /define_dimensions - Define Business Dimensions
======================================================

Purpose
-------
Defines up to 4 business dimensions for a specific file key in a validator atom.
Supports both:
  - Custom validator atoms (created via /create_new)
  - Template validator atoms (from /validate_* endpoints)

Input Parameters
----------------
Form Data:

1. validator_atom_id (required, string)
   - Unique identifier of the validator atom.
   - Must exist in MongoDB or in-memory cache.

2. file_key (required, string)
   - Specific file key within the validator's schema.
   - Must match an existing file key in the validator's stored schema.

3. dimensions (required, string)
   - JSON array of dimension objects (maximum 4 allowed).
   - Each dimension object must contain:
     * id   (string, unique): Dimension identifier
     * name (string, unique): Human-readable dimension name

Example Input
-------------
[
  {"id": "region", "name": "Region"},
  {"id": "category", "name": "Category"},
  {"id": "brand", "name": "Brand"},
  {"id": "channel", "name": "Sales Channel"}
]

Process Flow
------------
1. Input Parsing and Validation
   - Parses `dimensions` as JSON array.
   - Ensures non-empty list of objects.
   - Enforces maximum of 4 dimensions.
   - Validates each dimension contains non-empty `id` and `name`.
   - Prevents duplicate IDs or names.

2. Validator Existence Check
   - Looks up validator in MongoDB via `get_validator_atom_from_mongo`.
   - Falls back to memory/disk via `get_validator_from_memory_or_disk`.
   - Returns 404 if validator atom not found.

3. File Key Validation
   - Verifies that `file_key` exists in the validator's schema.
   - Returns 400 if file key is invalid.

4. Storage and Persistence
   - Converts dimensions to dictionary format:
     { "dimension_id": { "id": ..., "name": ... } }
   - Stores to MongoDB via `save_business_dimensions_to_mongo`.
   - Updates in-memory cache (`extraction_results`) for runtime access.
   - In-memory failures are logged but non-blocking.

Output Response
---------------
Success Response (HTTP 200)
---------------------------
{
  "status": "success",
  "message": "Business dimensions defined successfully for file key 'sales_file.csv' (2 dimensions)",
  "validator_atom_id": "validator_123",
  "file_key": "sales_file.csv",
  "validator_type": "custom",
  "dimensions": {
    "region": {"id": "region", "name": "Region"},
    "category": {"id": "category", "name": "Category"}
  },
  "dimensions_count": 2,
  "max_allowed": 4,
  "dimension_details": {
    "dimension_ids": ["region", "category"],
    "dimension_names": ["Region", "Category"],
    "created_at": "2025-06-23T11:30:00"
  },
  "mongodb_saved": true,
  "in_memory_saved": "success",
  "next_steps": {
    "assign_identifiers": "POST /assign_identifiers_to_dimensions with validator_atom_id: validator_123",
    "view_assignments": "GET /get_identifier_assignments/validator_123/sales_file.csv"
  }
}

Error Responses
---------------
HTTP 400 - Bad Request
  - Invalid JSON format in `dimensions` parameter.
  - `dimensions` is not a list/array.
  - More than 4 dimensions provided.
  - Missing required fields (`id` or `name`).
  - Duplicate IDs or names in the request.
  - Invalid or non-existent `file_key`.

HTTP 404 - Not Found
--------------------
{
  "detail": "Validator atom 'your_validator_id' not found"
}

HTTP 500 - Internal Server Error
--------------------------------
  - Failed to persist dimensions in MongoDB.
  - Unexpected server errors during processing.
  - In-memory update failures (logged but non-blocking).

Business Dimensions Structure
-----------------------------
Dimension Object Format:
{
  "id": "unique_identifier",
  "name": "Human Readable Name"
}

Storage Format:
{
  "dimension_id": {
    "id": "dimension_id",
    "name": "Dimension Name"
  }
}

Key Features
------------
Dual Validator Support
  - Custom validators: From `/create_new` endpoint.
  - Template validators: From `/validate_*` endpoints.
  - Automatic detection and handling for both.

Validation Constraints
  - Maximum 4 dimensions per file key.
  - No duplicate IDs or names.
  - Fields `id` and `name` must be non-empty.
  - Validates `file_key` against validator schema.

Storage Strategy
----------------
  - Primary: MongoDB for long-term persistence.
  - Secondary: In-memory cache for runtime performance.
  - Fault tolerance: Continues if in-memory update fails.

Integration Workflow
--------------------
  - Define dimensions: This endpoint
  - Assign identifiers: `/assign_identifiers_to_dimensions`
  - View assignments: `/get_identifier_assignments/{validator_atom_id}/{file_key}`

Use Cases
---------
  - Business Intelligence: Define dimensions for analytical slicing.
  - Data Modeling: Establish dimensions for OLAP-style schemas.
  - Validation Setup: Prepare structural definitions for data validation.
  - Schema Organization: Group related columns under named dimensions.

====================================================================================

Purpose
-------
Assigns classified identifier columns to previously defined business dimensions and
saves the assignments in the business dimensions structure.  
Supports both:
  - Custom validator atoms (from /create_new)
  - Template validator atoms (from /validate_* endpoints)

Input Parameters
----------------
Form Data:

1. validator_atom_id (required, string)
   - Unique identifier of the validator atom.
   - Must exist in MongoDB or in-memory cache.

2. file_key (required, string)
   - Specific file key within the validator's schema.
   - Must have defined business dimensions and classified columns.

3. identifier_assignments (required, string)
   - JSON object mapping dimension IDs to arrays of identifier column names.
   - Each dimension can have multiple identifiers.
   - All identifiers must be from previously classified identifier columns.

Example Input
-------------
{
  "region": ["market", "geography"],
  "category": ["brand", "category_name"],
  "time": ["year", "month", "week"],
  "channel": ["sales_channel"]
}

Process Flow
------------
1. Input Parsing and Validation
   - Parses `identifier_assignments` as a JSON object.
   - Ensures non-empty dictionary format.
   - Each dimension must be mapped to a non-empty list of identifiers.

2. Validator Existence Check
   - Primary: MongoDB via `get_validator_atom_from_mongo`
   - Fallback: Memory/disk via `get_validator_from_memory_or_disk`
   - Verifies `file_key` exists in validator's schemas.

3. Business Dimensions Retrieval
   - Primary: MongoDB via `get_business_dimensions_from_mongo`
   - Fallback: legacy format
   - Ensures dimensions exist for specified `file_key`.

4. Classification Data Retrieval
   - Primary: MongoDB via `get_classification_from_mongo`
   - Fallback: Memory/disk
   - Extracts available identifiers from `final_classification.identifiers`.

5. Assignment Validation
   - Ensures all dimension IDs exist in defined dimensions.
   - Ensures all assigned identifiers are valid and classified.
   - Prevents identifiers from being assigned to multiple dimensions.
   - Each dimension must have at least one assigned identifier.

6. Data Update and Persistence
   - Adds `assigned_identifiers` and `assignment_timestamp` to each dimension.
   - Saves updated structure to MongoDB via `update_business_dimensions_assignments_in_mongo`.
   - Updates in-memory `extraction_results`.
   - Memory update failures are logged but non-blocking.

POST: /configure_validation_config - Configure Custom Validation Rules
========================================================================

Purpose
-------
Configures custom validation conditions and optional data frequencies for specific columns
within a validator atom's file schema. Enables advanced rule setup beyond basic type validation.

Input Parameters
----------------
JSON Request Body:

1. validator_atom_id (required, string)
   - Unique identifier of the validator atom.
   - Must exist in MongoDB or memory cache.

2. file_key (required, string)
   - Specific file key within the validator's schema.
   - Must match an existing file key.

3. column_conditions (required, object)
   - Dictionary mapping column names to lists of validation conditions.
   - Each column can have multiple rules.
   - All columns must exist in the validator schema.

4. column_frequencies (optional, object, default: {})
   - Dictionary mapping column names to data frequency strings.
   - Valid values: ["daily", "weekly", "monthly"].

Example Input
-------------
{
  "validator_atom_id": "sales_validator_123",
  "file_key": "sales_data.csv",
  "column_conditions": {
    "sales_amount": [
      {
        "operator": "greater_than",
        "value": 0,
        "error_message": "Sales amount must be positive",
        "severity": "error"
      },
      {
        "operator": "less_than_or_equal",
        "value": 1000000,
        "error_message": "Sales amount exceeds maximum limit",
        "severity": "warning"
      }
    ],
    "region": [
      {
        "operator": "in_list",
        "value": ["North", "South", "East", "West"],
        "error_message": "Invalid region specified",
        "severity": "error"
      }
    ]
  },
  "column_frequencies": {
    "sales_date": "daily",
    "week_ending": "weekly"
  }
}

Validation Operators
---------------------
Numeric:
  - greater_than, greater_than_or_equal, less_than, less_than_or_equal, equal_to,
    not_equal_to, between

String:
  - contains, not_contains, starts_with, ends_with, regex_match

List:
  - in_list, not_in_list

Date:
  - date_before, date_after, date_between

Process Flow
------------
1. Input Validation
   - Validates presence of required fields: `validator_atom_id`, `file_key`, `column_conditions`.
   - Validates `column_conditions` and `column_frequencies` are dictionaries.
   - Ensures frequency values (if provided) are among valid options.

2. Validator Existence Check
   - Primary: MongoDB via `get_validator_atom_from_mongo`.
   - Fallback: Memory/disk via `get_validator_from_memory_or_disk`.
   - Validates that `file_key` exists in schema.

3. Column Validation
   - All columns in `column_conditions` must exist in validator schema.
   - Reports available columns if a mismatch occurs.

4. Condition Structure Validation
   - Each column’s conditions must be a list of valid objects.
   - Each rule must include:

MinIO Operations Summary - AtoM Validation System

Configuration

  - Secret Key: pass_dev

Core Functions
--------------
Connection Management
---------------------
check_minio_bucket()
  - Validates connection to MinIO
  - Ensures specified bucket (validated-d1) is accessible
  - Runs automatically at system startup or validation init

File Upload
-----------
upload_to_minio(file_content_bytes, filename, validator_atom_id, file_key) → dict
  - Uploads validated file to MinIO bucket
  - Constructs object path as:
      `{validator_atom_id}/{file_key}/{timestamp}_{filename}`
  - Uploads as binary stream with content-type: `application/octet-stream`
  - Returns:
      {
        "status": "success",
        "bucket": "validated-d1",
        "object_name": "...",
        "url": "http://10.2.1.65:9003/validated-d1/{object_name}",
        "etag": "...",
        "size_bytes": ...
      }

Key Features
------------
✓ Conditional Uploads
  - Upload triggered **only** if validation result is "passed" or "passed_with_warnings"

✓ Timestamped Object Naming
  - Uses `YYYYMMDD_HHMMSS` format to ensure uniqueness and traceability
  - Example: `promo_template_20250623_1130/promo/20250623_113041_promo_data.csv`

✓ Organized Storage
  - Hierarchical object structure:
    `bucket/validator_atom_id/file_key/timestamp_filename`
  - Promotes ease of retrieval and audit logging

✓ Error Handling
  - Separate handling for:
    * `S3Error` (MinIO-specific)
    * General exceptions (I/O, encoding, network)

✓ Efficient Memory Handling
  - Uses `BytesIO` to stream file content into MinIO without writing to disk

✓ Metadata Ready
  - Upload result includes ETag, size, and constructed access URL

Upload Workflow
---------------
1. Validation Endpoint triggered
   → File read and processed into bytes

2. Object name generated:
   → `{validator_atom_id}/{file_key}/{timestamp}_{filename}`

3. File uploaded via `upload_to_minio(...)`
   → Response includes status, URL, and metadata

4. Upload results included in API response and saved in validation log

Integration
-----------
Upload Triggered By:
  - POST /validate
  - POST /validate_mmm
  - POST /validate_category_forecasting
  - POST /validate_promo

Storage Path Format:
  validated-d1/{validator_atom_id}/{file_key}/{timestamp}_{filename}

Access URL Format:
  http://10.2.1.65:9003/validated-d1/{validator_atom_id}/{file_key}/{timestamp}_{filename}

- Automatically store validated files for traceability
- Enable external access for downstream processing
